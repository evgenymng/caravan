# Задание 16. «Посылка между ноутбуками»

Разработайте приложение для передачи файлов между двумя компьютерами в локальной сети.

Отправитель выбирает файл и адрес получателя. Файл передаётся по сети частями. Получатель сохраняет уже успешно принятые части и подтверждает их получение.

Если соединение оборвалось, передача должна продолжиться после повторного подключения без повторной отправки уже подтверждённых частей.

Основная схема:

```text id="k1f5u9"
Ноутбук A                       Ноутбук B

file.zip
   ↓
разбиение на chunks
   ↓
chunk 0 ───────────────────────→ сохранить
        ←────────────────────── ACK

chunk 1 ───────────────────────→ сохранить
        ←────────────────────── ACK

chunk 2 ───── X connection lost
```

После восстановления:

```text id="6hh0tr"
повторное подключение
        ↓
получатель сообщает:
chunks 0 и 1 уже есть
        ↓
передача начинается с chunk 2
```

---

## 1. Два режима приложения

Приложение должно поддерживать минимум две роли:

```text id="93jjl1"
sender
receiver
```

Например:

```bash id="ikjclh"
file-transfer receive --port 8080
```

и:

```bash id="9a9lkp"
file-transfer send \
  --file ./archive.zip \
  --address 192.168.1.15:8080
```

Допускается:

- одно приложение с разными режимами;
- два отдельных executable.

---

## 2. Локальная сеть

Передача должна работать между двумя устройствами в одной локальной сети.

Например:

```text id="rqfe9k"
192.168.1.10
192.168.1.15
```

Передача только между двумя процессами через `localhost` для финальной демонстрации недостаточна.

На защите желательно показать передачу между двумя реальными устройствами.

Если это технически невозможно, допускается демонстрация на одном компьютере через разные процессы и порты, но реализация должна поддерживать работу по LAN.

---

## 3. Транспорт

Допускается использовать:

- TCP;
- HTTP;
- другой потоковый транспорт поверх TCP.

Если используется HTTP, нельзя считать обычную повторную загрузку файла целиком реализацией resume.

Необходимо самостоятельно реализовать передачу файла частями и восстановление состояния передачи.

---

## 4. Метаданные файла

Перед началом передачи отправитель должен сообщить получателю информацию о файле.

Минимально:

```text id="ugfgos"
transfer ID
имя файла
размер файла
размер chunk
количество chunks
контрольная сумма файла
```

Например:

```json id="1s2drz"
{
  "transferId": "4be271a1",
  "fileName": "archive.zip",
  "fileSize": 524288000,
  "chunkSize": 1048576,
  "chunks": 500,
  "checksum": "..."
}
```

---

## 5. Transfer ID

Каждая передача должна иметь идентификатор.

Например:

```text id="ylptxw"
4be271a1
```

По этому идентификатору получатель должен понимать:

```text id="mgsld9"
это новая передача
```

или:

```text id="eulc1o"
это продолжение ранее начатой передачи
```

Transfer ID должен сохраняться при повторном подключении.

---

## 6. Передача частями

Файл нельзя отправлять как один огромный блок.

Он должен быть разбит на chunks.

Например:

```text id="nkfkwy"
file size = 350 MB
chunk size = 1 MB
```

Получаем:

```text id="t4xflx"
chunk 0
chunk 1
chunk 2
...
chunk 349
```

Размер chunk должен быть фиксированным для конкретной передачи.

Рекомендуется сделать размер настраиваемым.

Например:

```text id="nz32kk"
256 KB
1 MB
4 MB
```

---

## 7. Большие файлы

Программа не должна загружать весь файл в оперативную память перед отправкой.

Недопустимый вариант:

```go id="s9hx58"
data, _ := os.ReadFile(path)
```

для файла в несколько гигабайт.

Отправитель должен читать только необходимую часть файла.

Например:

```text id="plz67k"
открыли файл
     ↓
прочитали chunk N
     ↓
отправили
     ↓
перешли к следующему chunk
```

Аналогично получатель не должен хранить весь принимаемый файл в памяти.

---

## 8. Нумерация chunks

Каждая часть должна иметь однозначный номер или offset.

Например:

```text id="fneh44"
chunk index = 42
```

или:

```text id="yug1lh"
offset = 44040192
```

Получатель должен понимать, куда именно записать полученную часть файла.

---

## 9. Проверка целостности chunk

Для каждой передаваемой части должна вычисляться контрольная сумма.

Например:

```text id="69nrqp"
SHA-256
```

Отправитель передаёт:

```text id="r8tfjn"
chunk number
chunk size
chunk checksum
chunk data
```

Получатель:

```text id="i5mnvm"
получил chunk
    ↓
вычислил checksum
    ↓
сравнил
```

Если checksum совпал:

```text id="11jm3o"
ACK
```

Если нет:

```text id="tbpbb7"
ошибка
```

Повреждённая часть не должна считаться успешно принятой.

---

## 10. Подтверждение получения

Получатель должен подтверждать успешно сохранённые части.

Например:

```text id="gs5hp1"
SEND chunk 42
     ↓
RECEIVE + verify
     ↓
ACK chunk 42
```

Только после ACK отправитель может считать часть подтверждённой.

---

## 11. Главное правило resume

После получения ACK часть считается успешно переданной.

При восстановлении соединения уже подтверждённая часть не должна передаваться повторно.

Например:

```text id="bwnwsf"
chunk 0 → ACK
chunk 1 → ACK
chunk 2 → ACK
chunk 3 → ACK

connection lost

chunk 4 → не подтверждён
```

После восстановления:

```text id="i0fnrr"
chunk 0 — skip
chunk 1 — skip
chunk 2 — skip
chunk 3 — skip

продолжить с chunk 4
```

---

## 12. Кто хранит состояние

Состояние уже принятых частей должно храниться на стороне получателя.

Например:

```text id="uiiy20"
transfer 4be271a1

received:
0
1
2
3
7
8
```

Не следует полагаться только на память отправителя.

После разрыва соединения получатель должен сообщить отправителю, какие части у него уже есть.

---

## 13. Состояние передачи должно переживать разрыв

Получатель должен сохранять информацию о неполной передаче.

Например:

```text id="qvf3xj"
data/
  4be271a1/
      metadata.json
      received.map
      file.part
```

Конкретный формат выбирается самостоятельно.

Если приложение получателя не завершалось, состояние может храниться в памяти и на диске.

Для более надёжного решения рекомендуется сохранять состояние на диск.

---

## 14. Resume после перезапуска

Желательно, чтобы незавершённая передача могла продолжиться даже после перезапуска receiver.

Минимально обязательный сценарий:

```text id="78ivsh"
соединение разорвалось
↓
процессы продолжают работать
↓
подключение восстановили
↓
передача продолжается
```

Усиленный вариант:

```text id="0z1c8t"
receiver перезапустили
↓
состояние восстановилось с диска
↓
передача продолжается
```

Если поддерживается только первый вариант, это необходимо явно указать в README.

---

## 15. Повторное подключение

После повторного подключения отправитель сообщает:

```text id="kxmx4x"
transfer ID
```

Получатель отвечает информацией о состоянии передачи.

Например:

```text id="o53luu"
last confirmed chunk = 37
```

Это допустимо только если chunks всегда принимаются строго последовательно.

Более общий вариант:

```text id="q9j0am"
received chunks:
0-37
40-45
```

Способ представления состояния выбирается самостоятельно.

---

## 16. Последовательная передача

Минимально достаточно передавать chunks последовательно:

```text id="fwykg4"
0
↓
1
↓
2
↓
3
```

Параллельная отправка нескольких chunks не обязательна.

Это позволяет сосредоточиться на:

- протоколе;
- ACK;
- integrity;
- reconnect;
- resume.

Дополнительная параллельная передача допускается после корректной реализации базового варианта.

---

## 17. Итоговая проверка файла

После получения всех chunks необходимо проверить контрольную сумму всего файла.

Например:

```text id="n7drg3"
SHA-256(sender file)
        ==
SHA-256(receiver file)
```

Только после успешной проверки передача получает статус:

```text id="4m1g1y"
completed
```

Если итоговая checksum не совпала:

```text id="zy3c21"
failed
```

Полученный файл нельзя считать корректным.

---

## 18. Временный файл

До завершения передачи файл рекомендуется хранить как временный.

Например:

```text id="50c499"
video.mp4.part
```

После успешной итоговой проверки:

```text id="ceijdq"
video.mp4.part
     ↓
video.mp4
```

При незавершённой передаче `.part` сохраняется для resume.

---

## 19. Разрыв соединения

Необходимо корректно обрабатывать:

- закрытие соединения;
- timeout;
- reset соединения;
- выключение Wi-Fi;
- временную потерю сети.

Разрыв передачи не должен автоматически уничтожать уже принятые данные.

Состояние должно перейти, например, в:

```text id="o9vcd8"
interrupted
```

или другое аналогичное состояние.

---

## 20. Timeout

Сетевые операции не должны ждать бесконечно.

Необходимо предусмотреть timeout минимум для:

- установления соединения;
- чтения;
- записи;
- ожидания ACK.

Значения должны быть обоснованы и описаны.

---

## 21. Повторная отправка неподтверждённой части

Если отправитель отправил chunk, но не получил ACK:

```text id="zin68s"
SEND chunk 15
        ↓
receiver сохранил chunk
        ↓
ACK потерян
        ↓
connection lost
```

После reconnect может оказаться, что chunk 15 уже есть на receiver.

Отправитель не должен автоматически считать его потерянным.

Сначала необходимо узнать состояние receiver.

Receiver сообщает:

```text id="w8j18y"
chunk 15 already received
```

и повторная передача не требуется.

---

## 22. Идемпотентность chunk

Получение одного и того же chunk повторно не должно повреждать файл.

Например:

```text id="kf3z9r"
chunk 15
```

уже сохранён.

Если по ошибке он пришёл ещё раз, система должна:

- определить, что chunk уже существует;
- либо безопасно перезаписать ту же область после проверки;
- либо вернуть ACK без повторной записи.

Выбранное поведение должно быть описано.

---

## 23. Ошибки файловой системы

Необходимо корректно обрабатывать:

- недостаток места на диске;
- отсутствие прав;
- невозможность создать файл;
- ошибку записи;
- исчезновение исходного файла;
- изменение исходного файла во время передачи.

Ошибка не должна приводить к panic.

---

## 24. Изменение исходного файла

Если исходный файл был изменён во время незавершённой передачи, продолжать старую передачу опасно.

Например:

```text id="y3wcc3"
transfer started
file size = 500 MB

после разрыва:
тот же path
но содержимое уже другое
```

При resume необходимо убедиться, что речь идёт о том же файле.

Для этого можно использовать:

```text id="xdk01u"
file size
full checksum
transfer ID
```

Если файл изменился, старую передачу необходимо отклонить либо создать новую.

---

## 25. Имена файлов

Получатель не должен слепо доверять имени файла, переданному по сети.

Например, нельзя позволить:

```text id="n3evcg"
../../important.file
```

и записать данные за пределами директории загрузок.

Необходимо безопасно обрабатывать имя файла и сохранять его только внутри разрешённой директории.

---

## 26. Состояния передачи

Рекомендуемый набор:

```text id="22uhgx"
created
transferring
interrupted
completed
failed
```

Допускается другая модель.

Финальное состояние должно быть однозначным.

---

## 27. Просмотр состояния

Необходимо показывать состояние передачи.

Например:

```text id="y4suuy"
transfer: 4be271a1
file: archive.zip

status: transferring

received:
322 / 500 chunks

progress:
64.4 %

received:
337 MB / 524 MB
```

Допускается CLI-вывод.

Отдельный frontend не требуется.

---

## 28. Прогресс

Во время передачи необходимо отображать минимум:

```text id="r4e24u"
количество переданных bytes
общее количество bytes
процент выполнения
```

Дополнительно:

```text id="io4i5k"
скорость
ETA
количество chunks
```

---

## 29. Протокол

Необходимо явно описать используемый протокол обмена.

Например:

```text id="v607yd"
HELLO
    ↓
TRANSFER_META
    ↓
RESUME_STATE
    ↓
CHUNK
    ↓
ACK
    ↓
CHUNK
    ↓
ACK
    ↓
...
FINALIZE
    ↓
COMPLETE
```

Конкретный формат сообщений выбирается самостоятельно.

Можно использовать:

- собственный бинарный протокол;
- JSON-заголовки + binary payload;
- HTTP endpoints;
- другой понятный вариант.

---

## 30. Границы сообщений

Если используется raw TCP, необходимо помнить:

```text id="82bvzi"
один Write()
```

не равен:

```text id="mvx5py"
один Read()
```

TCP является потоком байтов.

Следовательно, собственный протокол должен иметь framing.

Например:

```text id="q2gal9"
message length
message type
payload
```

или другой корректный способ определения границ сообщений.

На защите необходимо объяснить, как receiver понимает, где заканчивается одно сообщение и начинается следующее.

---

## 31. Context и завершение

Долгие операции должны поддерживать отмену через `context.Context`.

При завершении приложения необходимо:

1. прекратить принимать новые передачи;
2. закрыть сетевые соединения;
3. завершить выполняющиеся операции;
4. сохранить состояние незавершённых передач;
5. закрыть файлы;
6. корректно завершить программу.

---

## 32. Ограничение ресурсов

Нельзя бесконтрольно принимать неограниченное число одновременных передач.

Необходимо установить максимальное количество активных соединений или передач.

Например:

```text id="jb0uud"
max concurrent transfers = 4
```

Выбранное ограничение должно быть конфигурируемым или явно заданным.

---

## 33. Безопасность конкурентной записи

Если несколько goroutine работают с состоянием одной передачи, необходимо обеспечить корректную синхронизацию.

Недопустимы:

```text id="ea1km7"
data race
двойное подтверждение
повреждение bitmap chunks
конкурентная запись в одну область файла
```

Проект должен успешно проходить race detector.

---

## 34. Что не требуется

В рамках задания не требуется:

- работа через интернет;
- NAT traversal;
- UPnP;
- WebRTC;
- шифрование;
- TLS;
- авторизация;
- GUI;
- облачное хранилище;
- распределённая система;
- торрент-протокол;
- P2P между множеством участников.

Основной сценарий:

```text id="e7f7a8"
один sender
↔
один receiver
```

в локальной сети.

---

## 35. Обязательные технические требования

Программа должна:

- быть написана на Go;
- передавать файлы по локальной сети;
- поддерживать файлы значительно больше размера chunk;
- передавать файл частями;
- не загружать весь файл в память;
- нумеровать chunks;
- проверять целостность каждой части;
- подтверждать успешно полученные части;
- хранить состояние незавершённой передачи;
- поддерживать повторное подключение;
- продолжать передачу после разрыва;
- не отправлять повторно уже подтверждённые части;
- корректно обрабатывать потерянный ACK;
- проверять целостность готового файла целиком;
- использовать временный файл до завершения;
- безопасно работать с именами файлов;
- иметь сетевые timeout;
- корректно обрабатывать ошибки сети и диска;
- ограничивать число одновременных передач;
- иметь graceful shutdown;
- не содержать data race.

Проект должен проходить:

```bash id="7bbex3"
go test ./...
```

и:

```bash id="qcx6c3"
go test -race ./...
```

---

## 36. Обязательные тесты

Необходимо проверить минимум следующие сценарии.

### Обычная передача

```text id="1u6pqy"
sender
↓
100 MB file
↓
receiver
↓
checksums equal
```

### Файл больше chunk

Например:

```text id="cga9oj"
file = 100 MB
chunk = 1 MB
```

Должно быть передано около:

```text id="yxvxle"
100 chunks
```

### Разрыв соединения

Передать часть файла:

```text id="lffey1"
40 %
```

Разорвать соединение.

После reconnect передача должна продолжиться примерно с оставшихся:

```text id="1blk8j"
60 %
```

а не с нуля.

### Потеря сразу после сохранения chunk

Receiver сохраняет chunk.

Соединение разрывается до того, как sender получил ACK.

После reconnect этот chunk не должен обязательно передаваться заново: receiver сообщает фактическое состояние.

### Повреждение chunk

Изменить данные тестовой части.

Checksum должна обнаружить ошибку.

Повреждённая часть не считается принятой.

### Итоговая checksum

После завершения:

```text id="7lqmu7"
sender SHA-256
==
receiver SHA-256
```

### Изменённый исходный файл

Начать передачу, изменить исходный файл и попытаться продолжить старый transfer.

Сервис должен обнаружить несоответствие и не продолжать передачу как будто файл тот же.

---

## 37. Демонстрация

На защите необходимо показать:

1. запуск receiver;
2. подключение sender;

Главный сценарий защиты:

```text id="72xgtt"
файл состоит из 100 chunks

0..49 → успешно переданы
        ↓
оборвали соединение
        ↓
подключились снова
        ↓
receiver сообщает:
0..49 уже получены
        ↓
sender начинает с 50
        ↓
50..99
        ↓
full checksum
        ↓
completed
```

Главная идея задания:

```text id="252zwc"
TCP гарантирует доставку байтов
в рамках одного живого соединения.

Но если соединение умерло,
новое соединение ничего не знает
о предыдущем.

Resume — это уже ответственность
прикладного протокола.
```
